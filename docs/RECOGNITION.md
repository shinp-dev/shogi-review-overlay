# 将棋ウォーズ・将棋クエスト盤面画像比較

## 認識アルゴリズム

1. 盤面調整済みの9×9の各マスを検査する。線の混入を避けるため、**上下左右の外周8%を除外**し、残り84%を32×32に最近傍サンプリングする。
2. 輝度（77R+150G+29B）/256 が115未満の画素を黒、それ以外を白とする。81マスの特徴量はフレームの1回の画素配列取得で計算する。
3. 32個の横方向黒画素数と32個の縦方向黒画素数（64要素）で先後別テンプレートを比較する。将棋ウォーズ・将棋クエストともに基本駒16種＋成駒12種（先後6種ずつ）。基本駒には別画面の補助テンプレートも登録し、**駒種単位で上位6種**を選び、その駒種に属する全テンプレートの最良一致を利用する。評価式は縦横プロフィールcosine 55%＋画素cosine 45%。
4. 黒画素70未満は空きマス。最高一致度0.74未満、または2位との差0.075未満のマスは未確定として局面解析を拒否する。
5. 盤上40枚のケースは王将・駒種別合計を検査してSFENへ。持ち駒が生じている場合は確定済みの前局面から1手の合法手差分で復元する。復元不能な局面はSFENを手入力する。
6. 検出位置は初期設定グリッドを中心に最大±4実画面ピクセルで探索。2px間隔の粗探索→周囲1pxの微調整で、81マス全体の信頼度・王将・駒数整合性から採用する。採用したdx/dyは手動位置設定に加算せず別管理し、矢印・候補表示の座標にのみ反映する。局面やエンジンが不確実な場合は候補を消す。
7. やねうら王Material版にUSI MultiPV=1〜3で渡す。投了ボタンの有無による認識停止は行わない（対局後の振り返りでのみ使用すること）。

画像比較に使う素材は app/src/main/assets/shogi_templates_v1.txt（将棋ウォーズの既存基本駒）・shogi_wars_variants_v1.txt（ウォーズ別画面の基本駒）・shogi_wars_promoted_v1.txt（ウォーズ成駒）・shogi_quest_templates_v1.txt（将棋クエスト基本駒）・shogi_quest_variants_v1.txt（クエスト別局面の基本駒）・shogi_quest_promoted_v1.txt（クエスト成駒）。ユーザー提供の振り返り画面から**駒セルのみを32×32白黒パターンに抽出**。元画像、対局者名、UI全体の画像は格納しない。アプリ選択に応じてテンプレートを切り替え、手動盤面位置と自動補正も別々に保存する。

## 将棋クエストの初期対応

- 提供された691×1536の9路レビュー画面の枠を基準に、初期位置（left=0.012, top=0.179, width=0.977, height=0.480）を設定。画面サイズやバナーによってズレるため、初回は手動調整が必要。
- スクリーンショットの盤上34枚について、32×32の輝度マスク比較をオフライン検査し、基本駒種と向きが判別できることを確認（Android実機は未検証）。
- 先後の香・桂・銀・金・玉／王・飛・歩は盤上の実画素、角は持ち駒領域の画像を切り出して仮登録。持ち駒角は盤上角と大きさが違うため、角の認識は保証しない。
- 2026-11-23に提供された別の691×1536局面から、成駒6種類（と・成香・成桂・成銀・馬・龍）を抽出し、先手向き6種類＋後手向き馬の実画像テンプレートを追加。ほかの後手向き成駒5種類は180度回転による暫定テンプレート。
- その局面の81マス（盤上32枚、空白49マス）を独立した回帰用二値マスクとして保存し、成り・向き・駒種と、画像の持ち駒を合わせた総数40枚の整合性をテスト。旧画像34枚の回帰テストも新しい認識器で実施。
- 別の駒テーマ、盤面の上下反転、途中局面からの持ち駒復元は未対応。振り返りは初期局面から1手ずつ再生する必要がある。


## 実測・制限

- 将棋ウォーズについては既存の初期盤面・数手進めた盤面の2画像に加え、今回の成駒6種類を含む691×1536画像から抽出した81マスの白黒マスクを照合。盤上31枚の駒種・先後・成り状態と空白50マスを検証した。別の端末倍率、アニメーション、後手成駒の実画像では未検証。
- 盤中央の「先手」「後手」などの文字装飾は低一致度・低黒画素数で誤認識を避ける。ただし別の大きな装飾や駒デザイン変更では判定できない可能性がある。
- 将棋ウォーズの成駒6種（と、成香、成桂、成銀、馬、龍）を追加。画像の先手向き駒から抽出し、後手向きは180度回転で仮生成した。**後手成駒の実画像照合は未検証**。将棋クエストの成駒も6種類を登録したが、馬以外の後手向きは回転画像からの仮生成。両アプリとも持ち駒領域は直接分類せず、合法手1手の履歴追跡に依存する。
- 認識が未確定の局面で推奨手を勝手に出さず、表示を消す。誤認識防止を速度より優先する。
- Android上の動作・バッテリー消費・認識時間は実機で未測定。
- 盤面は画面下が先手の向き専用。対局中と振り返りの厳密な識別は未実装。


## 将棋クエストの持ち駒欄（途中局面からの再開）

- 盤面の直上・直下にある金色の持ち駒を画素の色分布から位置検出し、上下の所有者（後手／先手）を判別する。アイコン間隔や種類数が変わっても検出する。
- 駒種は各側の持ち駒アイコンから抽出した32×32二値テンプレート（`shogi_quest_hand_icons_v1.txt`）で判定。未撮影の角度は180度回転画像で暫定対応。
- 赤い枚数数字は16×24の二値形状（`shogi_quest_hand_digits_v1.txt`）で判定し、数字なしは1枚とみなす。2/3/6は提供画像から抽出、ほかの数字は合成参考データで実画面未検証。
- 結果が不明瞭、読み間違い、または盤上＋持ち駒の**駒種別総数40枚の不整合**なら直接SFENの使用をやめ、従来の1手差分追跡を利用する。偽の候補手は提示しない。
- 1手差分が追える場合は、その結果の手番・手数を優先する。途中から直接始める場合の手番は設定画面の値に依存し、手数はSFENの1として復元する。手番や棋譜の完全な自動解析ではない。
- 持ち駒OCRは導入しない。実機MediaProjectionや別の画面縮尺・表示テーマは未検証。


## 将棋ウォーズ：持ち駒の動的な並び

- 2026-11-24に提供された2枚の振り返り画像で、**上側に角・歩、下側に歩・香・金**と**上側に角・歩、下側に歩のみ**の配置を確認。表示順・表示数によって位置が変わるので、固定x座標や「歩・香・桂・銀・金・角・飛」の固定順序には依存しない。
- 手動補正後の盤面を基準に、上・下の持ち駒欄を横方向に探索。提供画像の32×32白黒駒字マスクで所有者・駒種を分類し、黄色い個数表示は16×24の二値字形で判定（2・3のみ実画像登録）。
- 持ち駒を誰が何枚持っているかが決定したとき、盤上の駒と合計**種類ごとの40枚**で完全一致する場合に限ってSFEN生成。一部だけの判別や未知の個数表示は推定で埋めず、従来の1手ずつの追跡に戻す。
- 別の画像に写る後手の角・歩／先手歩を、独立した二値マスクとして回帰テスト。画像ファイル自体は保存しない。
- そのため現時点のウォーズ持ち駒画像認識は**実写のある5方向・駒種の組み合わせ**と2・3に限定。その他の駒・別テーマ・実機MediaProjectionは未検証。初手から1手ずつ進める方式は引き続き利用可能。
